\section{5G Networks}

Until \ac{5g}, each successive generation of mobile networks delivered incremental gains in throughput and reach while preserving the same fundamental paradigm: a purpose-built, hardware-centric network optimized for a single traffic type. 5G was designed from the ground up as a programmable, multi-service platform capable of simultaneously serving heterogeneous vertical industries with vastly different performance requirements, instead of simply aiming to increase throughput and extend data rates \cite{ZieglerArchitecturevision5Gera2016}.

To address these diverse requirements, the ITU-R IMT-2020 framework defined three canonical usage scenarios: \ac{embb}, targeting peak data rates in the tens of gigabits per second; \ac{urllc}, targeting sub-millisecond latency and near-perfect reliability for mission-critical applications; and \ac{mmtc}, supporting connection densities of up to one million devices per square kilometer for \ac{iot} deployments \cite{IMTFrameworkoverallobjectivesfuturedevelopment2015}. The 5G system achieves this flexibility through the adoption of key enabling technologies such as \ac{nfv}, \ac{sdn}, Network Slicing, and \ac{mec}, that transform the network into a software-defined, service-based, distributed infrastructure \cite{HermosillaDeployment5GNetworkApplicationsMultidomain2022, antonyfranklin2020MultiaccessEdgeComputing}.

Figure \ref{fig:5g_architecture} shows the reference architecture for the service-based architecture of the \ac{5g} core, where each function exposes REST-based \acp{api} over the Service-Based Interface. The upper functions belong to the control plane, while the bottom functions relate to the user plane.

The most relevant network functions of the \ac{5g} core are briefly described as follows \cite{3GPP5GSystemarchitecture5GSystem2026}:

\begin{itemize}
    \item The \ac{upf} is responsible for user plane packet handling such as routing/forwarding, marking and \ac{qos} enforcing;
    \item The \ac{amf} manages registration, connection, mobility management and authorization and authentication;
    \item The \ac{smf} manages the establishment, modification, and termination of data sessions by configuring the \ac{upf};
    \item The \ac{pcf} defines and enforces rules for \ac{qos}, charging and access control;
    \item The \ac{nef} exposes the capabilities and events of the \ac{5g} core to external applications and third parties in a controlled, authorized way;
    \item The \ac{nrf} allows network functions to register and discover each other, acting a central service registry and discovery point for the Service Based Architecture;
    \item The \ac{udm} stores and manages subscriber data and handles authentication credential generation and access authorization;
    \item The \ac{ausf} performs the actual authentication of the \acp{ue} using the credentials from the \ac{udm};
    \item The \ac{nssf} determines which network slice instances should serve the \ac{ue} based on the set \acp{sla} based on subscription info, policies, and requested slice types;
    \item The \ac{nssaaf} performs authentication and authorization of \acp{ue} specific to a network slice, enabling per-slice access control beyond the primary authentication;
    \item The \ac{af} represents external or operator applications which are able to interact with the \ac{5g} core via the \ac{nef}.
\end{itemize}

% ran
Complementing the core, the \ac{ran} is responsible for the radio interface between \acp{ue} and the network, handling wireless transmission, scheduling, and handover. In the 5G architecture, the \ac{ran} is realized by \acp{gnb}, which connect to the core via the NG interface and to one another via the Xn interface for mobility coordination \cite{3GPPNGRANArchitecturedescription}.

\subsection{5G-Advanced and the 6G Vision}

Starting with Release 18 (Rel-18) \cite{3GPPDigitalcellulartelecommunicationssystemPhase} and continuing through Release 19 (Rel-19) \cite{3GPPDigitalcellulartelecommunicationssystemPhaseRel19}, the \ac{3gpp} standardization roadmap extended the 5G baseline through a series of incremental releases, collectively referred to as 5G-Advanced. These releases introduce native \ac{ai} and \ac{ml} capabilities across both the \ac{ran} and core network, enabling data-driven optimization of resource management, handover decisions, and load balancing. Further enhancements address cross-domain network slicing, extended support for \ac{xr} and immersive services, reduced-capability device classes targeting \ac{iiot} and wearables, and significant improvements in energy efficiency. The cross-domain slicing enhancements in particular extend slice-aware \ac{mec} resource management beyond single-operator boundaries, establishing the groundwork for the multi-domain federation requirements being formalized for the sixth generation under the ITU-R IMT-2030 framework.

The ITU-R defines six usage scenarios for IMT-2030, expanding upon the three scenarios introduced in IMT-2020 while introducing new scenarios that previous generations were not designed to support \cite{IMTFrameworkoverallobjectivesfuturedevelopment2023}:

\begin{itemize}
    \item \emph{Immersive Communication}: Extends \ac{embb} to cover high-bandwidth, low-latency interactive experiences, including \ac{xr}, holographic telepresence, and multi-sensory communications;
    \item \emph{Hyper Reliable and Low-Latency Communication}: Extends \ac{urllc} to address mission-critical use cases where failure to meet reliability and latency     requirements carries severe consequences, such as industrial automation, emergency services, and telemedicine;
    \item \emph{Massive Communication}: Extends \ac{mmtc} to support the connection of a massive number of devices and sensors across domains such as smart cities, logistics, agriculture, and environmental monitoring.
    \item \emph{Ubiquitous Connectivity}: Addresses the digital divide by extending meaningful coverage to rural, remote, and underserved areas through interworking with non-terrestrial networks and other access systems.
    \item \emph{Artificial Intelligence and Communication}: Integrates distributed \ac{ai} workloads, including model training, inference, and computing resource 
    orchestration, natively into the network infrastructure, enabling use cases such as autonomous driving assistance and digital twin creation;
    \item \emph{Integrated Sensing and Communication}: Extends the radio interface beyond connectivity to provide sensing capabilities, including positioning, object detection, environmental monitoring, and real-time mapping, without requiring dedicated sensor hardware.
\end{itemize}

\section{Network Functions Virtualization}

% intro and driving factors
Traditional network architectures relied heavily on proprietary hardware appliances for each specific function, such as firewalls, routers, and load balancers. These hardware-based solutions are not only costly but also inflexible, making it challenging to scale and adapt to dynamic network demands \cite{ChiosiNetworkFunctionsVirtualisationIntroductionBenefits}. 

% core concept
\ac{nfv} allowed the transition from hardware-dependent network functions to virtualized software solutions. By leveraging virtualization techniques, \ac{nfv} allows for dynamic deployment and lifecycle management of various network functions on \ac{cots} hardware as \acp{vnf}. This approach decouples the functions of the network from proprietary hardware, enabling them to run on standard servers, storage, and networking equipment.

% advantages
\ac{nfv} brings several advantages over hardware-centric approaches \cite{ETSINetworkFunctionsVirtualisationNFVArchitectural2014}. \acp{vnf} run on \ac{cots} hardware, eliminating dependency on proprietary appliances and reducing both capital and operational expenditure. Functions can be deployed, scaled, and relocated dynamically across geographically distributed sites, enabling a degree of flexibility that static hardware cannot match. Standardized, open interfaces promote a multi-vendor ecosystem where \acp{vnf} and infrastructure components from different providers can coexist, and the rapid instantiation of new services reduces time-to-market significantly.

% cnf shoutout
In the recent years, the dominant virtualization technologies have since shifted from hypervisor-managed virtual machines to containers orchestrated by platforms such as Docker\footnote{https://www.docker.com/} and Kubernetes\footnote{https://kubernetes.io/}, giving rise to \acp{cnf}: network functions decomposed into microservices and managed through cloud-native orchestration primitives. Container-based deployments offer lower per-instance overhead, faster startup times, and compatibility with \ac{cicd} deployment workflows \cite{ValantasisExperimentalEvaluationOrchestrationSoftwareVirtual2021}.

\subsection{NFV Reference Architecture}

Figure \ref{fig:nfv_reference_architecture} presents the \ac{etsi} \ac{nfv} reference architecture, which organises the framework into three main domains: the \acp{vnf}, the \ac{nfvi}, and the \ac{mano}. \acp{vnf} are software implementations of network functions that execute on \ac{nfvi} resources; the \ac{nfvi} encompasses the compute, storage, and networking hardware and software that host them. The \ac{mano} domain coordinates the lifecycle of both \acp{vnf} and \ac{nfvi} resources, and is itself subdivided into three building blocks:

\begin{itemize}
    \item \emph{\acp{vnfm}}: responsible for managing the lifecycle of \acp{vnf}, including instantiation, scaling, updating, and termination. It interacts with both the \ac{vim} and \ac{nfvo} to ensure the \ac{vnf} operates as intended within the \ac{nfv} infrastructure.
    \item \emph{\acp{vim}}: manages the \ac{nfv} infrastructure resources, such as compute, storage, and networking, within a single administrative domain. It provides resource abstraction and allocation, enabling the \ac{nfvo} and \ac{vnfm} to deploy and manage \acp{vnf}.
    \item \emph{\acp{nfvo}}: is responsible for orchestrating and managing network functions across multiple \ac{vim} instances and ensuring the overall coordination of resources and services within the \ac{nfv} environment. It also handles policy-based resource optimization and \ac{sla} management.
\end{itemize}

The other components of the framework are the \ac{oss}/\ac{bss}, which allows for \ac{nfv} service providers to interact with the \ac{nfv} infrastructure, enabling service provisioning, billing, and customer management; the Service, \ac{vnf} and Infrastructure Descriptions, which contain templates/descriptors used internally within the \ac{nfvo} to be translated into functional blocks; and the \ac{ems} which manages the functionality of one or more \acp{vnf}.

\section{Software Defined Networking}

In conventional network architectures, routing decisions, forwarding table computation, and policy enforcement are embedded within each device and managed independently through vendor-specific interfaces. With no global view of network state and per-device configuration as the only operational primitive, adapting to traffic demands or failures is slow and costly \cite{ONFSoftwareDefinedNetworksNewNorm2012}.

\ac{sdn} addresses these limitations by decoupling the control plane, responsible for computing forwarding decisions and enforcing network-wide policies, from the data plane, responsible for packet forwarding \cite{dhale2025SoftwareDefinedNetworkingSDN}. Network intelligence is consolidated in a logically centralized controller, which maintains a global view of the network topology and programs forwarding behavior across the infrastructure through standardized interfaces. This separation transforms the network into a programmable, software-driven resource that can be dynamically configured to meet changing service demands. By holding a consistent model of the full topology, the controller enables network-wide optimizations, such as coordinated policy enforcement, real-time flow rerouting, and automated provisioning, that are impractical when control is fragmented across independent devices. Furthermore, standardized southbound interfaces allow the controller to manage forwarding elements from heterogeneous vendors, and northbound \acp{api} expose network resources to higher-level orchestration systems, enabling tight coordination with complementary frameworks such as \ac{nfv}.

Beyond these core properties, \ac{sdn} enables \cite{dhale2025SoftwareDefinedNetworkingSDN}:
\begin{itemize}
    \item \emph{Vendor Agnosticism}: Standardized southbound interfaces reduce dependency on proprietary hardware and vendor lock-in;
    \item \emph{Dynamic Traffic Management}: The controller can reroute flows in real time based on current conditions, application requirements, or operator-defined policies;
    \item \emph{Network Automation}: Programmable \acp{api} support automated lifecycle management and coordination across the infrastructure.
\end{itemize}

\subsection{SDN Architecture}

Figure \ref{fig:sdn_architecture} shows an overview of the \ac{sdn} architecture, which is organized into three functional layers, each communicating through standardized interfaces.

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.6\textwidth]{figs/02/sdn.pdf}
    \caption{SDN three-layer architecture (adapted from \cite{ONFSoftwareDefinedNetworksNewNorm2012})}
    \label{fig:sdn_architecture}
\end{figure}

The infrastructure layer comprises the physical and virtual forwarding devices that constitute the data plane. These devices do not compute forwarding decisions autonomously; instead, they execute flow rules programmed by the controller, matching incoming packets against installed entries and applying the associated forwarding, dropping, or marking actions defined in their flow tables.

The control layer hosts the \ac{sdn} controller, which maintains a logically centralized, real-time model of the network topology and computes forwarding policies on behalf of the infrastructure devices. The controller translates high-level intents into low-level flow rules and disseminates these rules to the appropriate forwarding elements.

The application layer contains network applications that consume the controller's abstractions to implement higher-order network behaviors, such as load balancing, traffic engineering, access control, and network slice management. Applications interact with the controller without requiring knowledge of the underlying hardware topology or forwarding mechanisms.

These layers communicate through three categories of interface. The southbound interface connects the controller to infrastructure devices; OpenFlow is the dominant protocol, defining the message format and procedure for installing, modifying, and querying flow tables on forwarding elements \cite{AlghamdiSoftwareDefinedNetworkSDNOpenFlow2020}. The northbound interface exposes the controller's network model and programming capabilities to applications, typically through REST \acp{api} or intent-based abstractions; no single standard governs this interface, and implementations vary across controller platforms. An east-west interface can also be considered, enabling coordination between multiple controller instances and supporting distributed or hierarchical controller deployments where no single instance maintains a complete view of a large-scale network.

Within the \ac{5g} architecture, \ac{sdn} principles are directly reflected in the design of the \ac{upf}, whose forwarding behavior is programmatically controlled by the \ac{smf} through the N4 interface. This design applies the same control/data plane separation that defines \ac{sdn} natively within the 5G core, enabling per-session traffic steering, \ac{qos} enforcement, and data path programmability without relying on static, hardware-bound forwarding configurations \cite{3GPP5GSystemarchitecture5GSystem2026}.


\section{Network Slicing}

% intro to network slicing
The heterogeneous nature of 5G use cases imposes a fundamental tension on network design: the performance requirements of \ac{embb}, \ac{urllc}, and \ac{mmtc} services are not only distinct but often irreconcilable within a single, monolithic network configuration. A configuration tuned for peak throughput necessarily compromises the deterministic latency and reliability demanded by mission-critical applications, while one hardened for ultra-reliability wastes resources when serving bandwidth-intensive media services. Network slicing addresses this constraint by enabling the concurrent operation of multiple logically isolated, independently configured network instances over a shared physical infrastructure, each optimized for the characteristics of its target service \cite{zhang2017NetworkSlicingBaseda}.

% network slice definition
A network slice is an end-to-end logical network instance comprising a set of network functions and associated resources (compute, storage, and transport) configured and isolated to satisfy the specific \acp{kpi} of a given service. Each slice spans end to end, from the \ac{ran} through the transport domain to the 5G core, and is defined by a \ac{nst}, which captures the performance targets, resource budgets, and topology constraints that govern instantiation and operation. Slices are isolated from one another across the data, control, and management planes, ensuring that faults and congestion within one slice cannot propagate to others.

\begin{figure}[ht]
    \centering
    % \includegraphics[width=0.85\textwidth]{figs/02/network-slicing-concept.pdf}
    \caption{Network slicing concept: multiple isolated logical networks over shared physical infrastructure, enabled by \ac{nfv} (per-slice \ac{vnf} instances) and \ac{sdn} (per-slice flow isolation).}
    \label{fig:network_slicing_concept}
\end{figure}

% benefits of network slicing
From an operational standpoint, slicing yields several properties that a monolithic design cannot provide \cite{3GPP5GSystemarchitecture5GSystem2026}:
\begin{itemize}
    \item \emph{Logical Isolation}: Each slice operates as an independent network instance, ensuring that traffic, faults, and resource contention within one slice do not affect others;
    \item \emph{Customized \acp{qos}}: Slice-specific configurations enable delivery of differentiated service profiles tailored to each vertical, from high-bandwidth media delivery to ultra-reliable industrial control;
    \item \emph{Multi-tenancy}: Multiple operators, enterprises, or service providers can share the same physical infrastructure while receiving logically dedicated resources and isolated management planes;
    \item \emph{Rapid Service Deployment}: Slices can be instantiated, modified, and decommissioned programmatically through standardized interfaces, reducing the time-to-market for new services;
    \item \emph{Efficient Resource Utilization}: Resources can be dynamically allocated and reallocated across slices according to demand, improving overall infrastructure efficiency compared to statically partitioned, purpose-built networks.
\end{itemize}

% relation with nfv & sdn
Network slicing is not an independent abstraction but is technically realized through the joint application of \ac{nfv} and \ac{sdn}. \ac{nfv} provides the virtualization layer that enables per-slice network function instances to be created, configured, and terminated on shared \ac{cots} hardware. Without \ac{nfv}, deploying independent function sets per slice would require dedicated physical appliances for each service type, negating the shared-infrastructure principle that slicing depends upon. The \ac{nfvo} and \ac{vnfm} components of the \ac{mano} framework orchestrate the lifecycle of these per-slice \acp{vnf}, while the \ac{vim} allocates and tracks the compute, storage, and networking resources budgeted to each slice instance.

\ac{sdn} complements this by enforcing per-slice traffic isolation and steering in the data plane. The \ac{sdn} controller programs forwarding rules that segregate slice-specific flows across the shared physical underlay, and enforces policies that prevent cross-slice interference at the transport layer. This mechanism extends the control/data plane separation already present in the 5G core (where the \ac{smf} programs the \ac{upf} via the N4 interface) to an end-to-end scope spanning the \ac{ran}, transport, and core simultaneously.

Together, \ac{nfv} governs the function plane (instantiation, scaling, and termination of per-slice network functions) while \ac{sdn} governs the transport plane (isolation, steering, and policing of per-slice flows). The slice management layer coordinates both through \ac{mano} \acp{api} and \ac{sdn} controller northbound interfaces, translating high-level service requirements into concrete resource allocations and forwarding policies across the full network stack.

% network slices management
The management of network slices in the \ac{3gpp} architecture, as defined in TS 23.501 \cite{3GPP5GSystemarchitecture5GSystem2026}, is organized into three hierarchical functional layers, as illustrated in Figure~\ref{fig:network_slicing_management}:

\begin{itemize}
    \item \emph{\ac{csmf}}: translates high-level customer-facing service requirements into network slice requirements, acting as the interface between business intent and the network management plane;
    \item \emph{\ac{nsmf}}: manages the lifecycle of \acp{nsi}, coordinating the instantiation and operation of constituent sub-slices and enforcing end-to-end \acp{sla};
    \item \emph{\ac{nssmf}}: manages the lifecycle of individual \acp{nssi} within \ac{ran}, transport and core, allocating and configuring the specific resources required by each sub-slice.
\end{itemize}

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.8\textwidth]{figs/02/ns-management.pdf}
    \caption{Network Slicing Management Functions (adapted from \cite{ChahbarComprehensiveSurveyE2E5GNetwork2021})}
    \label{fig:network_slicing_management}
\end{figure}

% slices descriptors, fields and information
Network slices are identified through the \ac{nssai}, a collection of one or more \acp{snssai}. Each \ac{snssai} comprises two fields: the \ac{sst}, which encodes the service category, and an optional \ac{sd}, which allows operators to differentiate among multiple slices of the same service type. The \ac{3gpp} specification standardizes four \ac{sst} values: \ac{embb} (1), \ac{urllc} (2), \ac{mmtc} (3), and \ac{v2x} (4). The 24-bit \ac{sd} field provides an operator-defined namespace for further differentiation.

% slice selection
Slice selection is handled at registration time. The \ac{ue} includes a requested \ac{nssai} in its registration request, which the \ac{amf} forwards to the \ac{nssf}. The \ac{nssf} evaluates the request against the \ac{ue}'s subscription profile, operator policy, and current resource availability, returning an allowed \ac{nssai} and, where necessary, a redirection to an \ac{amf} set associated with the target \ac{nsi}.

% end-to-end slice meaning
An end-to-end \ac{nsi} is composed of multiple \acp{nssi}, one per network domain - \ac{ran}, transport and core. The \ac{ran} sub-slice configures the radio resources and \ac{ran} functions assigned to the slice; the transport sub-slice establishes the connectivity between the \ac{ran} and the core; the core sub-slice instantiates the relevant \ac{5g} core network functions with the appropriate configurations and policies. Sub-slices may be shared across multiple \acp{nsi} where isolation requirements permit, enabling more efficient use of underlying resources.

% slices lifecycle
The lifecycle of a network slice spans five phases: preparation, in which the \ac{nst} is onboarded and feasibility is verified; instantiation, in which the constituent \acp{nssi} are created and configured; activation, in which the slice begins carrying live traffic; operation, in which the slice is continuously monitored and dynamically adapted to changing demand; and decommissioning, in which the slice is gracefully terminated and its resources released. Lifecycle management is coordinated between the \ac{nsmf} and the domain-specific \ac{nssmf} instances, following the interface specifications defined in 3GPP TS 28.530 \cite{3GPP5GManagementorchestrationConceptsuse2026}.


\section{Multi-access Edge Computing}

Latency-sensitive applications, such as real-time video analytics, augmented reality, industrial automation, and autonomous vehicle coordination, expose a structural limitation of the centralized cloud model. By concentrating compute and storage in geographically distant data centers, the cloud introduces round-trip latencies on the order of tens of milliseconds, even under ideal network conditions. For applications that require deterministic, sub-millisecond response at the point of access, this is not merely a performance constraint but a functional barrier \cite{SatyanarayananEmergenceEdgeComputing2017}.

\ac{mec}, standardized by \ac{etsi} \cite{ETSIMultiaccessEdgeComputingMECFramework2025}, resolves this by extending cloud-computing capabilities to the edge of the \ac{ran}, co-locating compute, storage, and networking resources in direct proximity to the \ac{ue}. This placement eliminates the backhaul round-trip to the core, enabling service execution at or near the base station. By exposing these resources to authorized applications through standardized \acp{api}, \ac{mec} transforms the network edge from a passive radio access point into an active, programmable service execution environment. These properties are impractical to achieve in a centralized deployment:

\begin{itemize}
    \item \emph{Ultra-Low Latency}: Application execution at the network edge eliminates the round-trip to centralized data centers, enabling response times compatible with real-time and mission-critical use cases;
    \item \emph{Backhaul Offload}: Local processing of traffic at the edge reduces upstream bandwidth consumption, alleviating congestion on backhaul links and improving overall network efficiency;
    \item \emph{Data Locality}: Processing data in proximity to its source allows operators and enterprises to enforce data residency and sovereignty requirements without routing sensitive information to remote infrastructure;
    \item \emph{Application Mobility}: \ac{mec} supports the live relocation of application instances across hosts in response to \ac{ue} mobility, preserving service continuity without interruption.
\end{itemize}

\subsection{MEC Reference Architecture}

The reference architecture for \ac{mec}, as defined by \ac{etsi} in MEC GS 003 \cite{ETSIMultiaccessEdgeComputingMECFramework2025}, is presented in Figure \ref{fig:mec_reference_architecture}. The architecture is organized into two principal domains: the \ac{meh}, which hosts applications and exposes platform services, and the \ac{mec} Management system, which governs the lifecycle of applications and the allocation of resources across the deployment.

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.8\textwidth]{figs/02/mec-reference.png}
    \caption{ETSI MEC reference architecture \cite{ETSIMultiaccessEdgeComputingMECFramework2025}}
    \label{fig:mec_reference_architecture}
\end{figure}

The \ac{meh} comprises two co-located components: the \ac{mep} and the \ac{vi}. The \ac{vi} provides the compute, storage, and networking resources on which \ac{mec} applications execute, and includes a data plane responsible for enforcing traffic rules and routing flows among applications, services, and external networks. The \ac{mep} operates above the \ac{vi}, providing the service environment through which applications discover and consume \ac{mec} services, register their resource requirements, and interact with the broader network. Specifically, the \ac{mep} manages traffic rules, configures \ac{dns}, and hosts platform-level services such as location and radio network information.

\ac{mec} applications execute as virtualized entities (containers or virtual machines) within the \ac{meh}. Their interaction with the \ac{mep} and with one another is governed by three reference points: Mp1 connects applications to the \ac{mep}, enabling service registration and discovery, traffic rule activation, and session state relocation in response to mobility events; Mp2 connects the \ac{mep} to the \ac{vi} data plane, allowing the platform to steer traffic flows among applications, services, and external interfaces; Mp3 enables inter-platform communication between \ac{mep} instances on separate hosts, supporting coordinated service delivery across distributed deployments.

The \ac{mec} Management system is organized into two tiers. At the system level, the \ac{meo} maintains a global view of deployed hosts, available resources, and accessible services, and is responsible for the end-to-end lifecycle of \ac{mec} applications, including onboarding, instantiation, termination, and application relocation decisions across hosts. At the host level, the \ac{mepm} manages the operational lifecycle of applications on a single host, handling rule enforcement, conflict resolution, and \ac{dns} configuration, while the \ac{vim} allocates, monitors, and releases the virtualized resources required by those applications, reporting performance metrics and fault conditions to the \ac{mepm}.

These management functions interact through a set of Mm reference points. Mm1 connects the \ac{meo} to the operator's \ac{oss}, enabling application instantiation and termination requests to be submitted from the operational layer. Mm3 links the \ac{meo} to the \ac{mepm} for application lifecycle coordination and service management. Mm4 connects the \ac{meo} to the \ac{vim} for resource allocation and tracking at the host level. Mm5 links the \ac{mepm} to the \ac{mep}, supporting platform configuration, lifecycle support, and application relocation procedures. Mm2, Mm6, and Mm7 extend these interactions between the \ac{oss}, \ac{mepm}, \ac{vim}, and \ac{vi} for configuration, fault management, and performance monitoring. The \ac{oss} bridges the operational and business layers of the system, managing service provisioning, billing, and customer management, and receiving service delivery requests from the \ac{cfs} via the Mm8 reference point.

\subsection{MEC Integration with NFV, SDN, and Network Slicing}

\ac{mec} does not operate in isolation from the enabling technologies described in the preceding sections; rather, it builds directly on \ac{nfv}, \ac{sdn}, and network slicing to deliver its edge execution model \cite{DouchEdgeComputingTechnologyEnablersSystematic2022}.

The \ac{vi} within each \ac{meh} is, in architectural terms, an instance of the \ac{nfv} infrastructure deployed at the network edge. \ac{mec} applications execute as virtualized entities, such as virtual machines or containers, managed by a \ac{vim} that is functionally equivalent to its \ac{nfv}-\ac{mano} counterpart. The lifecycle procedures carried out by the \ac{mepm} and \ac{meo}, like application onboarding, instantiation, scaling, relocation, and termination, directly mirror the \ac{vnfm} and \ac{nfvo} procedures defined by \ac{etsi} \ac{nfv} framework, with the addition of mobility-driven relocation as an edge-specific operational requirement.

\ac{sdn} underpins the traffic steering that directs flows from \acp{ue} or from the core network to the appropriate \ac{mec} application. The Mp2 reference point between the \ac{mep} and the \ac{vi} data plane functions as a southbound control interface: the \ac{mep} installs traffic rules that redirect specific flows to registered application endpoints on the host. At a larger scale, \ac{sdn} controllers operating at the transport layer can steer \ac{ue} traffic toward the nearest or most appropriate \ac{mec} host as users move across the coverage area, enabling network-wide traffic management that complements the host-local rule enforcement provided by Mp2.

Network slicing extends \ac{mec} into a multi-tenant edge execution environment. A single \ac{meh} can host applications belonging to multiple concurrent slices, with compute, storage, and networking resources partitioned according to per-slice \acp{sla}. The \ac{nssmf}, acting on behalf of the \ac{nsmf}, can coordinate with the \ac{meo} and \ac{mepm} to instantiate slice-specific edge applications as components of the core or \ac{ran} sub-slice, ensuring that edge resource allocation is governed consistently with the end-to-end performance contract of the slice. This integration, sometimes referred to as slice-aware \ac{mec}, is the architectural basis for deploying differentiated edge services on the same physical host while preserving mutual isolation.


\section{Network Federation}

The preceding sections have established the individual technologies underpinning this thesis: \ac{5g} architectures provide the programmable substrate; \ac{nfv} and \ac{sdn} enable flexible instantiation and control of network functions; network slicing provides logical isolation and service differentiation; and \ac{mec} positions compute and storage at the network edge. Each of these capabilities has been described within the context of a single administrative domain; in other words, a single operator managing a coherent set of infrastructure and control systems. However, the scenarios motivating this thesis require seamless service delivery across the boundaries of independently administered networks. Multi-domain network federation is the mechanism that enables this cross-boundary coordination.

% intro to federation
Multi-domain network federation refers to the voluntary sharing of resources, capabilities, and services across distinct administrative domains under agreements that preserve each domain's operational autonomy and policy sovereignty. Unlike roaming, which has historically been mediated by static, bilaterally negotiated arrangements for user-plane connectivity, federation in the context of \ac{5g} and \ac{mec} is dynamic and programmable: operators negotiate and activate cross-domain resource commitments at runtime, through standardized interfaces, in response to observed demand.

% constraints of federation
The fundamental challenge of federation is coordinating across administrative trust boundaries without compromising domain sovereignty. Each operator controls its own \ac{mano} stack, resource allocation policies, and security perimeter. A federation framework must therefore define inter-domain interfaces through which capability advertisement, resource negotiation, and lifecycle coordination can take place without requiring either domain to expose its internal topology or proprietary configurations to the other. This separation between what is shared — available capacity, service endpoints, performance guarantees — and what remains internal is enforced at the federation boundary, typically through a dedicated federation gateway or brokerage layer.

% federation patterns
Federation interactions can follow several patterns, depending on the operational scenario:
\begin{itemize}
    \item \emph{Resource Brokerage}: A consumer domain acquires computational or network capacity from a provider domain to augment its own, with the commitment agnostic to any specific workload;
    \item \emph{Service Chaining}: An end-to-end service or network slice spans multiple domains, with each contributing a segment; the federation layer stitches these segments into a coherent, \ac{sla}-compliant service;
    \item \emph{Workload Offloading}: A domain experiencing transient resource saturation redirects application instances or traffic flows to a federated partner, maintaining service continuity through dynamic load redistribution.
\end{itemize}

% why federation matters for this thesis
These patterns map directly to the use cases motivating this thesis. High-density transient events, such as a major sporting event at a stadium, generate sudden capacity spikes that a private edge deployment alone cannot absorb; workload offloading to a public operator provides the elastic overflow capacity required. Cross-border \ac{ppdr} operations, in which first responders must maintain communications continuity as they cross administrative or national boundaries, require service chaining across independently administered networks. In both cases, the federation mechanism must activate dynamically and with minimal pre-configuration, since the resource demand is unpredictable in timing, magnitude, and geographic extent.

\subsection{GSMA Operator Platform Group}

% motivation
Mobile operators have historically deployed their infrastructure using proprietary vendor stacks and closed management interfaces, rendering their network capabilities — edge compute, connectivity services, and network slices — inaccessible to external parties through standardized, programmatic means. This fragmentation prevents the realization of cross-operator service delivery and impedes the dynamic multi-domain federation that 5G and \ac{mec} architectures are designed to support.

% gsma opg initiative and objectives
The \ac{gsma} Operator Platform initiative, developed by the Operator Platform Group (OPG), addresses this by defining a framework through which mobile operators can expose their network and edge capabilities to application developers, enterprises, and peer operators through standardized, programmable interfaces \cite{GSMAOperatorPlatformConceptArchitecture2022}. Three principal objectives guide the initiative: enabling vendor-agnostic capability exposure by abstracting over heterogeneous internal infrastructure; supporting programmable federation between peer operators without requiring pre-negotiated bilateral arrangements; and providing a unified \ac{api} surface through which application developers and enterprises can consume edge and network resources across multiple operators without per-operator integration effort.

    \centering

    \caption{GSMA OP reference architecture \cite{GSMAOperatorPlatformConceptArchitecture2022}}
    \label{fig:op_reference_architecture}
\end{figure}

% reference architecture overview
The \ac{op} reference architecture, illustrated in Figure \ref{fig:op_reference_architecture}, organizes the platform around a core capability layer flanked by three families of standardized interface. The \ac{op} core maintains a resource controller responsible for tracking available compute, connectivity, and slice resources; a service registry through which capabilities are advertised and discovered; and a capability advertisement engine that propagates availability to consuming parties. Surrounding the core, the platform exposes three interface families: the \ac{nbi}, connecting the platform upward to application consumers; the \ac{sbi}, connecting it downward to the underlying infrastructure; and the \ac{ewbi}, connecting peer \ac{op} instances laterally for inter-domain federation.

% nbi
The \ac{nbi} exposes operator capabilities to application developers, enterprises, and vertical service providers. Through the \ac{nbi}, consumers can discover available edge compute locations and their resource profiles, query network slice offerings, and manage the lifecycle of their applications without knowledge of the operator's internal management stack.

% sbi
The \ac{sbi} connects the \ac{op} to the heterogeneous infrastructure underlying each deployment, abstracting over the operator's existing \ac{mec} hosts, 5G core network functions, and \ac{mano} components to present a normalized resource view to the partner \ac{op}. This abstraction allows the platform to maintain a consistent \ac{nbi} and \ac{ewbi} surface across operators running fundamentally different internal architectures, and is the mechanism through which the OPG initiative achieves its vendor-agnosticism objective.

% ewbi
The \ac{ewbi} enables federation between \ac{op}. It supports four federation procedures: capability advertisement, through which operators publish available resource types, quantities, and performance envelopes to other \acp{op}; resource reservation, through which a consumer operator requests and commits to a capacity allocation from a provider; \ac{sla} negotiation, through which performance parameters and remediation commitments are agreed between domains; and cross-domain slice extension, through which an active network slice in one domain is extended to encompass resources hosted by a peer operator. The trust boundary enforced by the \ac{ewbi} is a fundamental design property: what is shared, such as available capacity, service endpoints, and \ac{sla} commitments, is explicitly distinguished from internal network topology vendor configuration and the internal management plane, ensuring that federation does not require either operator to expose its operational infrastructure to the other.

% open challenges
Despite the comprehensiveness of the OPG framework, several operational challenges remain unresolved in the current specification. The \ac{ewbi} procedures assume that peer operators have established a trust relationship prior to live interaction; the bootstrapping of such relationships for previously unknown operators is not addressed. \ac{sla} enforcement across administrative boundaries — specifically, how a consumer operator verifies provider compliance for resources it cannot directly observe — remains an open problem. The scalability of capability advertisement under high resource-state churn and the absence of mechanisms for dynamic, zero-prior-agreement federation are particularly consequential for the transient-event and cross-border scenarios motivating this thesis, where demand is unpredictable and pre-negotiated bilateral arrangements are impractical.

\subsection{ETSI MEC Federation and OpenOP}

% mec federation background
As the deployment of \ac{mec} spread across operator networks, the single-domain scope of the original GS MEC 003 reference architecture proved insufficient for scenarios requiring cross-operator service continuity. ETSI \ac{mec} \ac{isg} addressed this gap through a two-stage process: first characterizing the problem space in a study-phase group report, then formalizing its outcome as normative \acp{api}. GR MEC 035 \cite{ETSIMultiaccessEdgeComputingMECStudy2021} established the scope of the federation problem, analyzing use cases including \ac{ue} mobility across operator boundaries, \ac{v2x} service continuity through foreign \ac{mec} deployments, and transient-event capacity overflow requiring cross-operator edge offload. ETSI White Paper No. 49 complemented this with non-normative deployment guidance, establishing terminology and classifying architectural options for federated \ac{mec} deployments \cite{ETSIMECFederationDeploymentConsiderations2022}.

% mec federation normative spec
The normative outcome of these studies is new \ac{mec} reference architecture variant for \ac{mecf} support, as illustrated in Figure~\ref{fig:mecf_architecture}, which includes the new \ac{mef} component, along with two reference points: the Mfm for \ac{mef}-to-\ac{meao} communication, and the Mff for \ac{mef}-to-\ac{mef} signaling. Furthermore, the \ac{gs} \ac{mec} 040 \cite{ETSIMultiaccessEdgeComputingMECFederation2023} specifies the Federation Enablement \acp{api} of the Mff.
% mff 040 specs are not complete yet, and probably will never be since focus was shifted to etsi oop

% etsi sdg oop: context and motivation
The normative work of ETSI \ac{mec} \ac{isg} and \ac{gsma} OPG produced coherent specifications, but operators and application developers lacked a vendor-neutral, deployable reference implementation against which to validate interoperability. To bridge this gap, \ac{etsi} established the \ac{sdg} Open Operator Platform (\mbox{OpenOP}). Unlike an ETSI \ac{isg}, which produces normative standards, an \ac{sdg} produces open-source software; OpenOP is therefore a code-producing initiative rather than a standards body. Its stated objectives are threefold: to provide a community reference implementation of the \ac{gsma} OPG; to serve as an experimentation platform for 6G testbed federation and telco cloud scenarios; and to generate implementation feedback that informs future standardization cycles \cite{ETSIOpenOPRelease12025}.

% release 1 architecture
Release 1 (2024--2025) is the first integrated release of OpenOP and organizes the platform around three principal components, as shown in Figure~\ref{fig:openop_architecture} \cite{ETSIOpenOPRelease12025}. The Open Exposure Gateway (OEG) functions as the northbound \ac{api} gateway, exposing telecom capabilities and edge cloud resources through \ac{camara} \acp{api}; it maps directly to the \ac{nbi} of the \ac{gsma} \ac{op} reference architecture and provides the interface through which application developers and enterprises consume edge resources across participating operators. The Service Resource Manager (SRM) handles application lifecycle orchestration and coordinates deployment across edge cloud zones by integrating with underlying \ac{nfv} \ac{mano} and \ac{mec} management stacks; it implements the core resource controller and service registry functions of the \ac{gsma} \ac{op} architecture and mediates the \ac{sbi} toward heterogeneous operator infrastructure. A third module provides intent-based interaction through a Model Context Protocol server backed by a large language model, translating natural-language operator intents into \ac{camara} \ac{api} calls. For federation, Release 1 implements the \ac{gsma} OPG \ac{ewbi} and aligns with the ETSI GS MEC 040 Mff reference point, supporting capability advertisement, resource reservation, and cross-domain service deployment between federated OpenOP instances.
